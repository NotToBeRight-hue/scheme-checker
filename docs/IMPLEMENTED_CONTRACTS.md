# Implemented DTO details and prototype choices

This supplements the original v3 contracts. IDs and revision counters are decimal strings; income is a decimal string. Profile dates and verification dates are ISO dates, stored as validated ISO VARCHAR values in this prototype schema. UTC event timestamps are ISO instant strings. No additional domain tables were introduced.

- Paginated responses: `{items, page, size, total}`; page is zero-based, size 1–100. Catalog sorting allows `name` or `id`; history, reviews and audits use newest ID first.
- Authentication responses: `{id,fullName,email,role,status}`. `/auth/csrf` additionally returns `authenticated` so an anonymous client avoids an unnecessary `/auth/me` failure. No token/hash in responses.
- Profile replacement takes top-level `dateOfBirth,stateCode,annualIncome,educationLevel,occupation,expectedRevision`. Blank/null optional fields become unknown. DOB must be YYYY-MM-DD, not future or over 130 years ago. Income is nonnegative DECIMAL(18,2). State codes use the standard two-letter allowlist in `Api.STATES`. Education and occupation are strings up to 100 characters. Every successful replacement advances revision once.
- Questions: `{id,label,type,options,active,revision}`. Types TEXT, NUMBER, DATE, BOOLEAN, SELECT, MULTI_SELECT. SELECT/MULTI_SELECT require distinct nonempty string options. Scheme question responses add `value` with the caller's saved answer. Null clears a submitted answer. Missing scheme-only answers are removed during replacement; omitted shared answers are retained. Numeric values are JSON numbers or decimal strings, dates ISO strings, boolean values JSON booleans, multiple selections string arrays.
- Schemes: `{id,name,categoryId,stateCode,description,benefits,guidance,sourceUrl,verifiedDate,synthetic,reviewerApproved,sourceMapping,exceptions,publishedVersionId,revision}`. Scope is a nullable state code. `sourceMapping` is an object from leaf node ID to source-section text. `questionIds` is an optional list during draft metadata creation/update. Detail additionally returns `rule` and `disclaimer`.
- Rule drafts take `{rule}` on create and `{rule,expectedDraftRevision}` on update. Responses `{id,schemeId,status,rule,revision,createdAt}`. Conditions on currency use exact BigDecimal comparison. Question definition meaning and published rule rows cannot be changed. Published scheme metadata is frozen to preserve its meaning; use a new draft scheme for metadata changes. A published scheme may receive new rule versions.
- Evaluations include the specified baseline fields, plus `id,userId,dateSensitive,snapshot,staleReasons`. Snapshot includes immutable `facts,rule,explanations,schemeName,synthetic`. Staleness reasons PROFILE_CHANGED, RULE_CHANGED, AGE_CHANGED. Age-dependent checks become stale when completed age actually changes, rather than merely at midnight. UNKNOWN without a dominating FALSE/TRUE returns INPUT_REQUIRED with `{missing:[fieldKey...]}` and no evaluation. All leaf explanations are retained when a decision is definitive.
- Suggestions include `{id,userId,type,schemeId,schemeName,description,proposedCriterion,sourceUrl,status,reviewNotes,revision,createdAt}`. Description/review notes/proposed criterion max 4000. HTTPS sources optional. Review accepts UNDER_REVIEW, NEEDS_INFO, ACCEPTED, REJECTED with notes and expectedRevision; resubmitted stale reviews conflict. Acceptance changes only review status.
- Additional complete admin routes: `GET /admin/overview`, `GET /admin/schemes`, `GET /admin/questions`, `GET /admin/schemes/{id}/questions`, `GET /admin/schemes/{id}/rules`, `POST /admin/categories`, `PUT /admin/categories/{id}`, `POST /admin/suggestions/{id}/convert`. Scheme conversion takes full draft metadata. Criterion conversion takes `{rule}` and creates a draft version on the suggested scheme. Conversion never publishes and is an explicit admin action. Category names are unique. Category/question/rule creation responses are 200; scheme creation is 201. The convert response is a direct new draft resource with 200.
- `GET /dashboard`: actual `profileCompleteness` percentage (five provided fields), `evaluationCount`, `pendingSuggestions`, and latest five `recentChecks`. `GET /admin/overview`: actual scheme and pending-suggestion counts. JDBC queries are read-only projections.
- Passwords use Base64(SHA-256(UTF-8 password)) then BCrypt, preserving all 8–128 characters without truncation. JWT issuer scheme-selector, audience scheme-selector-web, HS256, exact 900-second lifetime. Signing secret is at least 32 UTF-8 bytes. User role and ACTIVE status are checked in the database on every authenticated request.
- Login limits: 30 attempts/IP and 10/account in 15 minutes. Account is normalized email; IP is the network peer, never arbitrary forwarded headers. Limits include successful attempts, are process-local, and do not reset on login success. This is a single-process prototype. Security audits record registration, successful login/logout, failed login and rate limiting with no credentials, IPs or emails in audit payloads.
- Concurrency uses READ_COMMITTED and pessimistic locking refreshes, followed by expected-revision checks. Scheme publication locks the scheme, draft and linked question definitions. Evaluation holds the profile and active scheme version stable through snapshot insertion. There is no automatic retry. MySQL triggers also reject mutation/deletion of evaluations and published rule versions.
- Current scope intentionally has no persistent saved schemes/checklists, Aadhaar, AI, uploads, payments or government submission. The seeded application guidance explicitly offers no real application or benefit.
